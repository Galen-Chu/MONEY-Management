# 💰 MoneyCare · 產品計畫(P-PLAN)

> 個人財務統合 App(Invoice/ Mortgage/ 消費/ 信用卡/ 帳務/ 資產)——「半自動歸集 + 本機優先」路線。
> repo:Galen-Chu/MONEY-Management;對照家族:TEXT-Message(文管庫)/ MEDIA-Message(媒管庫)/ TIME-Management(TimeCare)。

---

## 🧭 定位 · Positioning

維護者自用的**單一介面財務總覽**:記帳為核心,發票/房貸/帳務資料以「可行的管道」半自動歸集,所有資料 100% 留在裝置上。不追求全自動串接(台灣現況不可行),追求「一目瞭然 + 低摩擦輸入」。

核心使用循環:**記一筆 / 歸集 → 帳戶淨值 → 月度統計 → 分類洞察**。

## 🧪 驗收基準 · P2–P4(2026-11-24 達成,收尾歸檔)

- **P2 消費管理**:發票——號碼 CRUD(2英+8數驗證)、獎號下載(稅務入口網公告頁確定性 URL)快取本機離線可用、九獎項比對 golden(115年7-8月實際獎號)、live 解析實測;現金流——歷史瀏覽月導覽、備註跨月搜尋、12 月現金流(轉帳不計/補零/跨年)
- **P3 資產管理**:五類型 CRUD+估值歷史(同日 tiebreak)、完整淨值=帳戶+持有−負債、淨值趨勢月末回推、備份五表(舊檔相容)
- **P4 CSV 匯入**:RFC4180/BOM/分隔符嗅探、欄位偵測可調、雙欄與正負單欄、民國/西元、逐筆 validateTxn;限 UTF-8
- **品質**:verify 128/128(本日+70);migration v4/v5 測試含交易順序;CJK 閘門持續把關

## 🧪 驗收基準 · P1 貸款模組(2026-11-24 達成)

- 貸款 CRUD:五類型(房/車/信/學/他)、本息/本金攤還、寬限期;驗證單一來源 `domain/loan.validateLoan`

## 🔭 P5/P6 開發確認與整合藍圖 · Blueprint(2026-11-25)

> 依維護者指示盤點主線後續兩項的可行性、資料流與整合部位;動手前仍依「串接類開發紀律」重查當下官方文件(規格以實測為準)。

### P5 載具發票查詢 · Carrier invoice sync

**前置(唯一硬門檻)**:以營業人(統編)向財政資訊中心「電子發票應用 API」平臺申請 appID(軟體 ID)。**無統編 → P5 不開**——現況(手動輸入號碼+自動對獎)已自足。

**定位(2026-11-25 維護者定案)**:**納入發票分頁,不另立載具管理**——發票頁加「載具」卡(綁定狀態+同步本月鈕),卡種/號碼/驗證碼以 Sheet 就地編輯(比照預算在統計頁、定期在設定頁的就地管理模式);同步結果併入「我的發票」標來源,手動輸入紙本發票並存。理由:載具發票=發票的另一個來源(同號碼格式/同期別數學/同對獎),拆開則「這期發票」要看兩處、期別導覽與比對邏輯重複;七分頁已滿載;CSV 匯入先例(來源入口+資料統一列表)。

**API 規格要點**(來源:電子發票應用 API 規格書;文字版以 phstudy/einvoice-api swagger 彙整核對,2026-11-25):

- `POST https://www.einvoice.nat.gov.tw/PB2CAPIVAN/invServ/InvServ`;appID 為全域查詢參數(ApiKeyAuth)
- `carrierInvChk`(version 0.3):cardType(`3J0002` 手機條碼/`1K0001` 悠遊卡/`1H0001` 一卡通/`2G0001` 愛金卡)、cardNo(載具號碼)、cardEncrypt(載具驗證碼)、timeStamp/expTimeStamp(防重放)、startDate/endDate(**必須同月**——逐月拉)、onlyWinningInv(Y=只抓中獎)
- 回傳:invNum(發票號)、sellerName、amount、invDate、invStatus(作廢等);另以 `carrierInvDetail` 逐張取品明(品名/數量/單價)
- 需 SignatureAuth(加簽)的 carrierInvDnt/qryCarrierAgg/ods——**不納入**(捐贈/彙總/大量查詢,自用無需)

**資料流**:發票頁「同步載具」→ 逐月 carrierInvChk → 存本機 → 既有九獎項比對自動跑 → 明細一鍵「轉交易」(草稿必經確認)。

**整合部位**(對應現有架構,零新依賴):

| 層 | 落點 | 說明 |
|---|---|---|
| data | `src/data/carrier-source.ts`(新) | 比照 `prize-source.ts`:可注入 fetcher、typed 錯誤、Jest 可測 |
| domain | `domain/invoice.ts` 擴充 | CarrierInvoice 模型;期別重用 `termOfDate`;對獎重用 `matchInvoice`;與手動輸入同號去重 |
| data | migration(下一版) | **擴充 `invoices` 表**(ALTER TABLE:source 欄+可空明細欄位+品明 JSON 快取)——單一列表單一查詢,與手動輸入「同號同期」自然去重;cardNo+驗證碼僅存本機 SQLite、**不入備份 JSON**(可分享檔案不含憑證) |
| state | `invoiceStore.syncCarrier()` | guard 模式;同月限制 → UI 以月為單位觸發 |
| UI | 發票頁 | 「同步載具」鈕+載具設定(卡種/號碼/驗證碼);結果併入「我的發票」並標來源;明細 → TxnSheet 預填(分類預設 other、備註=商家) |
| 建議層 | 與定期交易共用模式 | 「必經確認」——`validateTxn` 單一來源,確認才建交易 |

**估時與風險**:1 輪可完成(domain+source+store+UI+測試);風險=規格欄位名以實測為準、appID 審核期程未知。

### P6 通知管理 · Notification hub(2026-11-25 維護者定案改制)

**定位**:帳務通知歸集——把信用卡消費通知(簡訊/郵件)半自動轉為**交易草稿**,必經確認才入帳;與定期交易、P5 發票明細轉交易共用同一「建議層」模式(草稿卡掛今天頁,與定期待確認同區)。

**兩個通知源**:

- **簡訊(批次一,iOS 限制下的妥協形態)**:iOS 不開放第三方 App 讀簡訊匣、Android 亦需 dev client+原生模組——自用不做自動讀取。改為**貼上解析**:收到刷卡簡訊→複製→今天頁「貼上解析」鈕(expo-clipboard)→純函式解析器提取金額/末四碼/日期/商家(啟發式,CJK 關鍵字 `\u` 轉義維持閘門)→ 草稿。
- **郵件(批次二,遠期)**:Gmail 唯讀同步,鏡像文管庫 `src/services/gmail/` 分層(2026-11-25 實讀)——授權層 access token 不落地(換軌 `expo-auth-session`+refresh token 存 `expo-secure-store`,零後端,與 D5 相容);API 層純函式注入 token、5xx/429 退避重試、單封失敗跳過、併發設限、分頁;typed 錯誤碼;解析/建議層**規則式非 AI**(關鍵字表常數可測可調,介面預留 LLM 替換)。前置:Google Cloud OAuth client(`gmail.readonly` 為 restricted scope,自用未驗證 App 可用,僅警告與 100 人上限)+ 維護者信箱銀行信件盤點。

**分期**:

- **批次一(開發中)**:`domain/notification.ts` 簡訊解析純函式+Jest golden;待確認草稿(migration 新表+儲存庫+store:確認→TxnSheet 預填→`validateTxn` 入帳、忽略即刪);今天頁「通知待確認」卡+貼上解析鈕;錯誤併入 ErrorBanner。草稿屬暫時性質**不入備份**(同獎號原則)。
- **批次二(遠期)**:Gmail 同步源接入同一草稿管線;帳單到期提醒(帳單信解析繳款日→今天頁提示)。
